# Patina

A native Apple Silicon app that recreates the time-stretch and converter/filter character of the Akai S900/S950/S1000/S2000/S3000/S3200 samplers — the "cyclic" stretch behind decades of jungle, hip-hop and breakcore production — and, as of v2, the converter/filter/varispeed character of a wider heritage sampler roster (E-mu SP-1200, Fairlight CMI IIx, Ensoniq Mirage, E-mu Emulator II) that never had time-stretch at all. Built to succeed [Akaizer](https://the-akaizer-project.blogspot.com/) (Windows-only, closed-source, now end-of-life) with real-time audition and per-machine converter modelling it never had.

This is a clean-room implementation: no original manufacturer code, no ROM disassembly. The DSP is built from published service/owner's manuals, datasheets and (for the Akai voice chip only, as a behavioural reference, reimplemented rather than copied) MAME, then validated by ear against real hardware behaviour. See `/Users/locked/.claude/plans/snuggly-stargazing-deer.md` (v1) and `/Users/locked/.claude/plans/peppy-toasting-patterson.md` (v2) for the full research and design rationale.

**Gotchas fixed along the way:**
- A bare SwiftUI app run via `swift run`/the raw binary (no `.xcodeproj`, no proper `.app` bundle) launches with `NSApplication.ActivationPolicy.prohibited` by default — no window, no Dock icon, silently. Confirmed by querying `NSWorkspace.runningApplications` when the app appeared to hang with nothing on screen. Fixed with an explicit `NSApplicationDelegate` in `PatinaApp.swift` that sets `.regular` and activates on launch.
- Selecting **S900** in the Machine picker crashed the app: S900 has no time-stretch capability (added in the S950), so `maxStretchPercent` is `0.0` for it, making the Stretch slider's `25...0.0` range invalid — a guaranteed, 100%-reproducible crash on a completely normal user action. Found by actually driving the GUI (`osascript`/`System Events`), not by unit tests. Fixed two ways: the Stretch/Cycle controls are replaced with an explanatory message and the Live Audition/Process controls disabled whenever `machineProfile.supportsTimeStretch == 0`, and the range construction itself is clamped (`max(25.0, ...)`) as defense in depth rather than relying on the UI guard alone.
- `ConverterModel::quantize()` produced 2^bits + 1 levels, not 2^bits: clamping the scaled *value* to `≤ 1.0` after rounding lets an input that rounds to exactly +1.0 sail straight through (`1.0 > 1.0` is false), adding an extra level at the top. Caught by a test asserting the exact level count. Fixed by clamping the integer *index* to the standard asymmetric signed-PCM range (`[-levels/2, levels/2 - 1]`) before scaling, which is exactly right by construction rather than by a boundary check that can be dodged.
- **The resonant `ChamberlinSVF` diverged to ±infinity at its own default settings** (`filterCutoff01 = 1.0`, `filterResonance01 = 0.0` — fully open, no resonance boost). Stage 6's stability comment already flagged that the naive Chamberlin SVF gets "inaccurate/unstable as k approaches 2," and clamped `k` to 1.9 believing that was a safe margin below the boundary — it wasn't. An empirical sweep (all 16 resonance codes, 200k samples) found the real boundary at `k ≈ 1.23`, and at the worst-case damping (least resonance — the default) instability set in within a few hundred samples. Caught by stage 7's own longer-running INTELLIGENT tests (`FilterModelTests.cpp`'s shorter windows and non-default cutoffs happened not to exercise this at all). Fixed by clamping `k` to 1.1 (confirmed stable across every resonance code over 200k samples) and adding a hard per-sample state clamp as a backstop regardless — no input should ever be able to make this filter emit non-finite values into the rest of the pipeline. Real consequence: this SVF can't reach the full 20 Hz..Nyquist range its cutoff control implies; it caps out around 8 kHz at 44.1 kHz.

**Bug fixes (post-9-stage, real-use bugfix pass):**
- **CYCLIC was not an identity at 100% time factor — it audibly buzzed with nothing asked of it.** The crossfade in `_synthesizeCyclicBlocks` (`StretchEngine.cpp`) blended each block's tail against material read `overlap` samples into the *future* of the natural continuation, rather than the same output timebase — comb-filtering the last quarter of every block even when adjacent blocks were already contiguous and had no splice to hide at all. Reported as "the S950 sound seems distorted" — the initial hypothesis, that S950's 6-pole filter cascade over-attenuates versus S1000's 3-pole, was investigated and **measured, then refuted** (worst-case deviation ~4.7 dB at Nyquist, a tilt, not distortion): S950 was simply the only stretch-capable machine whose UI can't select INTELLIGENT (`hasModeSwitch == 0`), so it was the only place the underlying bug — present in CYCLIC on every machine — was ever heard. Fixed by reading the crossfade's second leg on the same output timebase as the first; verified to reduce artifact energy at 150–200% stretch by ~26 dB and make 100% a true identity (`Tests/CoreTests/StretchEngineTests.cpp`).
- **Live audition restarted playback on every slider movement, including filter/resonance-only changes.** `RealtimeStretchPlayer`'s worker did a full re-render and unconditionally reset the read position on every `setParams()`, with no distinction between a filter-only change (which can't affect buffer length) and a stretch-affecting one. Fixed with `StretchEngine::reapplyFilterOnly()` (redoes just the cached pre-filter buffer) plus `paramsDifferOnlyInFilter()` classification in the worker loop: a filter-only change now leaves the read position untouched, and a stretch-affecting change remaps it proportionally into the new buffer instead of snapping to 0 (`Tests/CoreTests/RealtimeStretchPlayerTests.cpp`).
- **No Stop control, and no signal when playback finished on its own.** `AudioPlaybackController.stop()` existed but was never exposed in the UI, and `scheduleBuffer` had no completion callback. Added a generation-counted completion callback (`onFinished`) and a Stop button wired to it.
- **Live Audition and offline Play Original/Processed could play simultaneously.** Two independent `AVAudioEngine`s (`AudioPlaybackController`, `LiveAuditionController`), and `_startLiveAudition()`/`_load()` never stopped the other one. Fixed by stopping offline playback whenever live audition starts or a new file loads.
- **Regression, caught immediately after the fix above shipped: dragging the Cycle slider during live audition on a stereo file made it sound "stereo width"/comb-y.** The read-position fix for the restart bug remapped position proportionally (`oldPos/oldLen * newLen`) on stretch-affecting changes instead of resetting to 0. `LiveAuditionController` runs one independent `RealtimeStretchPlayer` per channel, each with its own background worker — `oldPos` is a live, continuously-advancing value, and when two channels' workers process the same change at different wall-clock moments (ordinary thread-scheduling skew), each reads a *different* `oldPos` and remaps to a genuinely different, then permanently desynchronised, position. A mono test file during the original fix's verification couldn't have shown this — there's only one channel to desync against. Reverted to resetting to 0 on stretch-affecting changes (a fixed point every channel's worker converges on identically regardless of timing); the filter-only cheap path is unaffected, since it never touches the read position at all. New tests: a single-instance test confirming the reset, and a two-instance test that directly staggers two independent players through the same change and asserts they stay sample-identical.
- **Regression of the regression above: resetting to 0 on stretch-affecting changes stopped the two channels ever staying *permanently* desynchronised, but not from *transiently* diverging while the change was in flight — reported as the same "artificial stereo width" on every stretch-affecting knob (not just Cycle), still present after the fix above.** Each channel's `RealtimeStretchPlayer` published its own re-render and reset its own read position the instant its own worker finished, with zero regard for whether a sibling channel's worker (independent thread, independent completion time) had finished the SAME change yet — so for however long that gap lasted, one channel played the new render from 0 while the other kept playing the old one, which is genuinely different audio on each channel simultaneously. Rotary-knob dragging (finer-grained than the sliders it replaced) re-triggers this gap almost continuously through a drag, which is why it now reads as present on every knob rather than an occasional Cycle-specific glitch. Fixed by splitting publish from commit: a stretch-affecting re-render now lands in a `_pendingPublish` slot (`RealtimeStretchPlayer::commitPending()`/`hasPendingCommit()`) instead of going live immediately, and `LiveAuditionController`'s render callback only calls `commitPending()` on every channel once *all* of them report a pending commit — swapping every channel's buffer and resetting every channel's read position on the exact same audio frame, regardless of which worker actually finished first. The filter-only cheap path is unaffected (still publishes immediately; never needed the gate). New tests: a single-instance test locking in the deferred-publish contract itself (not visible to `pull()` until `commitPending()`), and a two-instance test that stages one channel's worker finishing before the other's and asserts they stay sample-identical throughout — not just once the dust settles, but during the gap itself, which the previous fix's test never actually exercised.

**User-feedback pass (first round of real use, post-9-stage):** seven requests, one of which turned out to already exist —
- **"Preview" button, promoted.** The "test before committing" ask was already built: the Live Audition toggle previews the fully processed result live. It just wasn't found, tucked below the knobs as a plain `Toggle`. Replaced with a prominent play/stop-style `Button` next to the knobs (same `_startLiveAudition`/`_stopLiveAudition` underneath, unchanged), plus a "recomputing…" busy light — which needed new C++: `akz_realtime_player_is_ready` turned out unable to drive it (it latches true forever after the first publish and can never report a *later* re-render), so `RealtimeStretchPlayer` gained a genuinely-toggling `_recomputing` atomic instead (`akz_realtime_player_is_recomputing`), set for the duration of each worker-thread render and polled by `ContentView` with hysteresis (150ms delay before showing, 250ms minimum once shown) so it doesn't strobe during a fast run of knob-drag re-renders.
- **Undo, parameters only.** `ParamSnapshot.swift` mirrors the ten stretch/filter parameters (`AkzStretchParams` itself has no Swift `Equatable` to compare against) and backs a plain `@State` undo/redo stack in `ContentView`, coalesced per-interaction via a new `onEditingChanged` closure on `RotaryKnobView` (mirrors SwiftUI's own `Slider`) so one knob drag is one undo step, not hundreds. Wired to a real Edit menu (`PatinaApp.swift`'s first `.commands` block) via `focusedSceneValue`, since `ContentView` has no view model a Scene-level menu could otherwise reach.
- **Revert to original.** The app was already non-destructive (`process()` re-decodes from `loadedSample.rawData`, never mutates it), so this just resets the nine non-machine params to the current machine's defaults and discards the render — one undoable step.
- **Double-click a knob to type a value, ⌥-click to reset.** Double-click was already reset-to-default; moved reset to Option-click (backed by a context-menu item so it stays discoverable) and gave double-click to a new inline `TextField` (`KnobCell.swift`), seeded with a bare number rather than the display string so parsing never has to know about any of the seven `%`/`st`/`smp` suffix formats.
- **Shift-drag a knob for fine adjustment.** 5× less sensitive. The one real design problem was the modifier changing mid-drag without the value jumping — solved by re-anchoring (normalized value, raw translation) at the moment Shift is pressed or released, rather than rescaling the whole drag retroactively.
- **Drag a file into the window to load it.** A window-wide `.onDrop` (not `.dropDestination(for: URL.self)`, which has a documented history of failing to decode Finder's own file-URL payload) routes to the existing `_load(url:)` funnel.
- **Drag the waveform out to export a .wav.** `.draggable`/`Transferable` (`ProcessedWavExport.swift`) — a file promise, so a cold or stale render doesn't stall the drag itself, only the drop. Renders fresh if needed (a drag-out of a stale state doubles as a Process); always exports `.wav` regardless of source container, unlike the Save panel's format-follows-source (safe: everything already normalises to little-endian internally). The per-channel render loop was extracted out of `process()` into `ProcessedRender.swift` so both share one implementation.

## Known limitations

Everything below is a deliberate scope decision flagged at the time, not an oversight discovered later — collected here so the state of the project is legible in one place rather than scattered across code comments.

- ~~S900/S950's variable sample rate/bandwidth control is not modelled.~~ **Fixed in v2 stage 4** (`RateModel.cpp`) — see the v2 section below.
- **The S2000/S3000 DAC's rising low-level distortion isn't modelled.** The real PCM69AP hybrid DAC's THD+N rises sharply into the decay tail (`ConverterModel.h`); reproducing that needs a verified transfer curve this project didn't have.
- ~~The resonant SVF can't reach its own advertised range.~~ **Fixed in v2's TPT SVF migration** (stage 6) — see the v2 section below.
- **The S1000's interpolator order is an assumption, not a citation.** Akai's own manual only states "24-bit algorithm, custom VLSI" (arithmetic precision, not filter order); this project assumes linear interpolation pending a by-ear revision (`Interpolator.h`).
- ~~The waveform display is not scrubable.~~ **Fixed in 2.1** (`WaveformView.swift`/`WaveformGeometry.swift`) — see the 2.1 section below.
- **8-bit AIFF would decode with the wrong signedness.** `PCMConversion.swift` decodes 8-bit as unsigned (the WAV convention); AIFF's 8-bit is actually signed. Not fixed because it hasn't come up — real sample libraries are practically always 16-bit.
- **INTELLIGENT mode's quality→search-range and width→crossfade mappings are this project's own design**, not derived from the hardware (no manual states the actual numeric ranges — plan section 2.2). The algorithm class (SOLA/cross-correlation search) is manual-confirmed; the specific curve mapping the 0–99 controls to sample counts is not. Measured too narrow at low `quality` (±33 samples against a 1323-sample frame at `quality=10`, not enough to phase-align even a 440 Hz tone) — a re-derive is in the backlog.
- ~~S3000/S3200 clip at fully-open cutoff.~~ **Fixed in v2's TPT SVF migration** (stage 6) — see the v2 section below.
- ~~Save Processed saves the last offline `Process()` result, not what live audition is currently playing.~~ **Fixed in v2 stage 11** — see the v2 section below (`Save Preview…`).
- ~~Recent files are session-only~~, not persisted. **Fixed in v2 stage 1** (`RecentFilesStore.swift`).
- **`_renderIsStale` can over-report staleness after 2.4's carry-over.** A parked-then-clamped value can make it flag a re-render as stale even when the audio would come out byte-identical (see the 2.4 section). Fixes with an `effective(for:)` projection that zeroes params the current machine ignores before comparing; not built yet.

## v2 — heritage sampler roster (in progress)

v2 reframes the app as a heritage sampler colour box: the machine roster is the point, not just Akai's time-stretch. Non-Akai machines (E-mu SP-1200, Fairlight CMI IIx, Ensoniq Mirage, E-mu Emulator II) are joining a roster that until now was six Akai machines only. Renamed from "Akaizer S" to **Patina** along the way — the app's job is adding vintage sonic character across a whole lineage of hardware, not modelling one manufacturer. Full plan, research citations and per-machine source availability: `/Users/locked/.claude/plans/peppy-toasting-patterson.md`.

Stages shipped so far:

1. **Rename** (`Package.swift`, `Info.plist`, `PatinaApp.swift`) — mechanical, no data touched.
2. **Preset format v2** (`PresetStore.swift`) — machine identity moved from `AkzMachine`'s raw enum value to a stable string id (`AkzMachineProfile.stableId`, e.g. `"akai.s950"`), so reordering or renumbering the machine enum can never remap a saved preset to a different machine again. A frozen migration table translates existing v1 files. Corrupt files are now preserved (`presets.json.corrupt-<epoch>`) instead of silently discarded. Recent files are persisted too (`RecentFilesStore.swift`), closing the "session-only" gap above.
3. **Filter topology + provenance as data** (`AkaizerCore.h`, `MachineProfile.cpp`) — `FilterModel.cpp` now dispatches on an explicit `AkzFilterTopology` field via a small factory instead of two overloaded numeric selectors, and a `[machine][stage]` provenance table promotes the `[M]`/`[I]` source-comment tags that were previously visible only to a reader of the code into data the app can eventually surface to a user.
4. **Param struct v2** (`AkzStretchParams.sampleRateHz`) — the first field added under an append-only scheme, guarded by three `static_assert`s (standard-layout, a per-field size sum, a literal size trip-wire) that turn a forgotten Swift-side mirror into a compile error rather than a silent bug.
5. **Sample-rate/bandwidth front end** (`RateModel.cpp`) — closes the S900/S950 bandwidth gap above: a real anti-alias filter followed by true decimation and zero-order-hold reconstruction, computed length-neutrally. Originally shipped with `sampleRateHz == 0` (every existing preset and default) meaning "no rate stage" — a true bypass — so it shipped with zero audible change until something explicitly set a rate. **2.1 removed that bypass entirely** (see below): the rate stage is now always engaged, at the machine's own top-end rate by default.
6. **DAC back end** (`RateModel::applyDacPath`) — a second zero-order-hold stage, run after transpose, modelling the real DAC's own reconstruction character at the machine's (possibly pitch-tracked) playback clock — distinct from the interpolator's own source-side sample selection.
7. **TPT SVF migration — a deliberate, audible change to existing S2000/S3000/S3200 renders.** The naive Chamberlin SVF (`k ≤ 1.1` stability clamp, ~8 kHz cutoff ceiling, uncompensated resonant-peak clipping — both "Known limitations" struck through above) is replaced by a zero-delay-feedback ("topology-preserving transform") SVF, unconditionally stable to Nyquist by construction. **A saved preset's resonant-filter sound on these three machines is no longer bit-identical to pre-v2 renders** — the cutoff can now genuinely reach the full 20 Hz–Nyquist range the control always implied, and a new `filterResonanceCompensation01` profile field (`[I]`, no manual specifies it) scales the signal path to keep the resonant peak from clipping. This is a fix, not a regression, but it is a real, audible break with v1 — by-ear fidelity bar: short cycle must still ring metallic, long cycle must still tremolo, exactly as before.
8. **Converter extension** (`ConverterModel.h`) — `quantize()`/`quantizeBuffer()` gain a `ConverterSpec` overload adding real companding (`Companding::MuLaw`, standard ITU G.711, `[I]` — the closest well-documented approximation to a real segment-law companding DAC) alongside the existing plain-bits entry point every pre-v2 call site still uses unchanged.
9. **Roster browser, control descriptors, provenance UI.** Stage 8 (a `SamplerModel` view-model extraction) was deliberately skipped — this environment can't interactively verify a large SwiftUI refactor, and a working, approved file wasn't worth the risk. Everything else lands on the existing `ContentView` instead: a sidebar **MACHINES** section (grouped by manufacturer, replacing the flat Machine picker), a new `MachineControls.swift` (finally testable, in the Audio target) generating each machine's knob row from `AkzMachineProfile` capability flags instead of a hand-written `if` chain, a **Bandwidth** knob for machines whose rate is a real control, and a "Modelled from…" panel in the machine header showing every stage's citation level (`CITED`/`INFERRED`/`N/A`) — v2's fidelity bar ("inference allowed, but must be visible in the UI") now has a UI, not just a data table.
10. **Four new machines join the roster: E-mu SP-1200 (1987), Fairlight CMI IIx (~1983), Ensoniq Mirage (1984), E-mu Emulator II (1984).** None have time-stretch — they're colour only. Two new filter topologies: `SsmLadder`, a real 4-pole transistor-ladder model (Stilson & Smith) for the Emulator II's SSM2045, capable of genuine self-oscillation at maximum resonance (bounded by a `tanh` soft-clip in the feedback path, not a hard clamp — the same failure class as the original Chamberlin SVF bug, fixed differently this time); and `CemStateVariable`, which reuses the already-unconditionally-stable TPT SVF math for Fairlight/Mirage's CEM3320/CEM3328-class VCFs. **Clean-room note:** Fairlight's profile was built entirely from its own service manual, the 1984 E&MM "Fairlight Explained" series, and CEM3320/SSM2045 datasheets — MAME's `fairlight/cmi01a.cpp` (which models exactly this circuit) was deliberately never opened, matching the Akai research's own MAME-as-behavioural-reference-only discipline. Every machine's per-stage citation quality is in its provenance table entries (`MachineProfile.cpp`) and visible via stage 9's "Modelled from…" panel — several fields are honestly flagged `[I]` where the research pass didn't turn up a precise citation (Mirage's DAC part number, Fairlight's exact anti-alias filter pole count, SP-1200's exact AA filter cutoff ratio).
11. **Save Preview…** closes the "no 'save what I'm hearing right now' path" gap above — renders fresh from the exact params live audition is already playing (`_currentParams()`, the same function both audio paths have always shared) without stopping it, so what gets saved is provably what's audible, not the last offline `Process()` result.

**Bug found and fixed along the way, not part of the original plan:** Preview, Process, and switching to a non-stretch machine during live audition were all silently gated on `supportsTimeStretch` — meaning S900 in v1, and all four new heritage machines in v2, could show their knobs but the Preview/Process buttons stayed disabled the whole time, and selecting one while live audition was running force-stopped it. Every one of these machines still has filter, transpose, and (some) bandwidth character worth previewing and processing; `StretchEngine.cpp`'s own `supportsTimeStretch` gate (v2 stage 3) already makes sending it stretch params harmless regardless of the UI. Fixed by removing the gate from all three call sites.

## 2.1 — user feedback release (in progress)

Five pieces of user feedback on the shipped 2.0 build, all traced back to specific code. Full plan: `/Users/locked/.claude/plans/immutable-weaving-brooks.md`.

1. **Stereo splice linkage in INTELLIGENT mode.** Both the offline path (`ProcessedRender.swift`, one `StretchProcessor` per channel) and the realtime path (`LiveAuditionController.swift`, one `RealtimePlayer` per channel, each with its own worker thread) picked their SOLA splice offset by cross-correlating that channel's OWN content -- L and R routinely chose different offsets at the same nominal position, heard as stereo decorrelation/comb filtering. `StretchEngine` now supports a `setSpliceGuide`: a shared offset table, derived from one analysis pass over the MID (summed) signal, that every channel's engine uses verbatim instead of searching its own content. Threaded through the C API (`akz_stretch_engine_set_splice_guide` / `akz_realtime_player_set_splice_guide`) and both Swift coordinators. Cyclic mode's block mapping was never affected (purely length-derived); this only changes INTELLIGENT mode's behaviour, and only for multi-channel sources.
2. **Bandwidth never bypasses, never 0.** `RateModel.cpp`'s `resolveSampleRateHz` used to resolve `sampleRateHz <= 0` to `hostSampleRateHz` -- a true bypass -- and `akz_stretch_params_default` set every machine's own default to that same 0 sentinel, so every machine (including fixed-rate SP-1200 and Emulator II, whose one rate is their whole defining character) shipped with the rate stage bypassed. 0 now resolves to the machine's own top-end rate instead, matching the field's own documented contract in `AkaizerCore.h`. The `>= source rate` early-out stays (you can't decimate a file upward, so a machine oversampling the loaded file is a genuine no-op, not a bug); the LCD's `rate` row now says `full` or `at source rate` so that no-op reads as legible rather than broken. **Changes how saved presets sound on S900, SP-1200, Emulator II, CMI IIx and Mirage** -- they now decimate/anti-alias where they previously didn't; migrated automatically on load (`PresetStore.swift`).
3. **Play Original wrong after loading a different-rate/channel-count file.** `AudioPlaybackController` connected its player to the mixer once, at the first-ever buffer's format, and never reconnected -- a later file at a different sample rate or channel count kept playing through the stale connection format, so the engine silently resampled it (heard as wrong speed plus artefacts). Fixed with a `needsReconnect` check before every `play()`.
4. **Cutoff clicks and lag in live preview.** The realtime worker's cheap filter-only path swapped a freshly refiltered buffer into the playing stream mid-stream with no crossfade -- an audible step at the swap, worse on longer samples where a play position is more likely to land right on one. `RealtimeStretchPlayer::pull()` now blends old-to-new over a short (5ms) equal-power crossfade at the exact real read position, instead of stepping straight to the new buffer.

5. **Playback bar + draggable start point over the waveform.** `WaveformView` was display-only; its header used to flag scrubbing as needing "real transport plumbing" this stage didn't budget for. New `WaveformGeometry.swift` (Audio target, unit-tested) provides the sample-index/x-position mapping, and fixes a real bug on the way: the old integer-division bucketing silently left the tail of a buffer between 1x and 2x the view width undrawn, and drew the original/processed traces at two different horizontal scales. A shared `referenceCount` (the longer of the two) now scales both. A playhead bar tracks whichever source is playing -- `AudioPlaybackController.playheadFraction` (from `AVAudioPlayerNode.playerTime`) for offline playback, `RealtimeStretchPlayer::readPosition01` (new, exported through the C API) for live audition -- polled at the same 20Hz the recomputing busy light already used. Clicking or dragging the waveform sets a start point that trims playback, live audition, and rendering (`ProcessedRender.render(startFrame:)`) to "from here to the end" -- deliberately NOT a param on `AkzStretchParams` (a preset naming a byte offset into some other file would be meaningless). The old whole-surface `.draggable()` for drag-out export moved to a small visible grip handle in the waveform's corner, since an AppKit-backed `.draggable()` and a SwiftUI `DragGesture` don't compose predictably on the same view -- incidentally making drag-out export discoverable for the first time (it used to be signalled only by a tooltip).

Verification: `swift test` and the CMake `AkaizerCoreTests` target both pass. Manual checks for what a test can't reach are in the plan file's Verification section.

## 2.2 — version display + resonance loudness (shipped)

1. **No version number shown anywhere in the UI.** `ContentView` now reads `CFBundleShortVersionString`/`CFBundleVersion` from `Info.plist` and shows it in the status footer.
2. **The Resonance control quieted the whole signal, not just the resonant peak.** The full passband-gain compensation every resonant machine applied (`filterResonanceCompensation01 == 1.0`) scaled the filter's *input* down by up to -18dB at max resonance to keep the peak from clipping -- but input-scale and output-scale are mathematically equivalent in a linear filter, so broadband content got hit exactly as hard as the peak it was meant to protect. Fixed with an output-side makeup gain (`sqrt(1/inputScale)`, clawing back half the loss in dB) plus a new soft-knee limiter (transparent below 0.98, asymptotes to unity above) to keep the now-boosted peak off full digital scale. Broadband loss at max resonance: -18dB -> ~-9dB. This loosens `FilterModelTests.cpp`'s old guarantee that the resonant peak never exceeds the input amplitude -- it can now, deliberately (that's the fix); it still never hard-clips.

**2.2.1 follow-up, same day:** the version footer above was showing Info.plist's stale default rather than the real release number -- bumped to match. Separately, "stereo phasing is back on the resonance dial during preview playback" turned out not to be caused by the resonance fix itself: it unmasked a pre-existing, already-known race in `RealtimeStretchPlayer`'s cheap filter-only path (each channel's worker published straight to `_published` the instant it finished, no cross-channel coordination), which only became audible once 2.2 restored broadband loudness at high resonance. Fixed by routing filter-only renders through the same `_pendingPublish`/`commitPending()` gate the stretch-affecting path already used.

4. **"Use as Source" chaining.** Requested directly: stretch, then stretch *the result* again, repeatably, for longer or gnarlier output (the classic S950 trick) -- deliberately with no limit modelled on how many times, per the user's own call not to reproduce the hardware's "enough already" ceiling. Reuses `saveProcessed()`'s exact `LoadedSample` construction, just hands it to the same source-adoption path `_load()` uses instead of a save panel -- in-memory only, no file write. Undo/redo are cleared on chaining (the parameter values survive, but every snapshot on either stack describes an edit against the *old* source).

**Already possible, no new code:** the "stretch a break, then pitch it back up to the original tempo for a metallic result" trick (destructive pitching) works today with Stretch + Transpose as-is. `StretchEngine::outputLength()` computes final length as `sourceLength * stretchRatio / semitonesToRatio(transposeSemitones)` -- so transposing up by `12 * log2(stretchPercent / 100)` semitones after a stretch cancels the length change and returns to the original duration, at a genuinely shifted (not pitch-preserving) pitch, which is the whole mechanism of the trick.

**Plugin direction (spike, not shipped in 2.3):** confirmed with the user that the target shape is an **AUv3 offline/clip processor** -- reusing today's whole-buffer engine as-is inside a plugin wrapper -- rather than a true realtime streaming insert. The engine's own docs already flag why the latter is a much bigger, separate effort: `AkaizerCore.h`'s own comment on `AkzRealtimePlayer` says its background-thread-recompute-plus-`shared_ptr`-swap design is "not something to build a shipped plugin's real-time path on unmodified," and every stretch mode here (CYCLIC splicing, INTELLIGENT's SOLA search) operates on a whole buffer already known in full, not a stream of fixed-size blocks with no look-ahead -- this is a sample mangler, not a realtime insert, and no UI work changes that. **Build-system spike, answered:** SwiftPM has no app-extension target kind (`swift package --help` confirms no `extension`/`appex` concept exists in the tool at all -- only executable/library/test/macro/plugin targets), and an AUv3 is packaged as an `.appex` bundle embedded in a host app, which SwiftPM cannot produce on its own. No DSP porting or plugin UI in 2.3; that Xcode project itself is 2.4+ scope.

**2.3.1/2.3.2 follow-up, real-use feedback:** item 3 and 4 above (and double-click) confirmed working, but three more surfaced:
- **Version footer still said 2.2** -- `Info.plist` wasn't actually bumped when 2.3 shipped (the exact same mistake 2.2's own follow-up made). Bumped to 2.3/3.
- **Dropping the (now whole-surface) waveform export back into its own window hung the app on next close.** First fix (2.3.1: reject a same-app marker type in `_handleDrop`) was real but incomplete -- diagnosed via temporary debug logging down to a drag that STARTS (materialize begins) but is never actually dropped anywhere (released outside any target, or the app quit mid-drag): `_materialize()`'s `await MainActor.run { onRendered?(...) }` stalled forever, only ever released by the OS's own ~60s unresponsive-app timeout. First attempt gated in `applicationShouldTerminate`, which fires *after* the window already closed -- Cancel had nothing left to cancel. ## 2.4 — carry settings across emulators, drop the MACHINES filter (shipped, user-confirmed)

Two user change requests (full rationale: `/Users/locked/.claude/plans/woolly-honking-pelican.md`). Both items hand-tested live by the user after shipping and confirmed working, including the round-trip-through-a-fixed-rate-machine case and live preview staying up across a switch.

1. **Switching emulator no longer resets your knobs.** Previously `_selectMachine` reset every parameter to the newly-picked machine's defaults -- which made comparing the same sample, same settings, across two samplers impossible: the thing you'd want to A/B was exactly what got thrown away. `ParamSnapshot.adapted(to:)` (`Sources/Audio/ParamSnapshot.swift`) replaces that reset with a carry-over, driven by two rules: a knob the *target* machine actually shows (per `MachineControls.controls(for:mode:)`) is clamped into that knob's own range (an S1000 at 1500% arriving on an S950, whose max is 999%, reads 999); a knob the target machine does *not* show is left completely untouched -- not reset, not clamped. That asymmetry is deliberate: clamping is lossy (S1000 1500% → S950 → S1000 gives 999 back, not 1500), parking is lossless (S1000 1500% → SP-1200, no stretch knob at all → S1000 gives 1500 back exactly), and clamping-when-visible is the right call, not a compromise -- a knob reading past its own travel while the DSP clamps the value anyway is the same illegibility 2.1 fixed for bandwidth. Nothing parked is ever audible or displayed meanwhile: the knob row, the LCD rows and the DSP itself are all gated on the same machine capability flags (`StretchEngine.cpp`'s `supportsTimeStretch`/`effectiveMode` gates, `FilterModel.h`'s resonance gate, `RateModel.h`'s fixed-rate collapse). Mode (CYCLIC/INTELLIGENT) carries across the same way -- the old force-to-CYCLIC on a no-mode-switch machine (S950) is gone, since every consumer already ignores an inapplicable mode without it. `_applySnapshot` (undo/redo, preset apply, revert) now self-adapts too, applying the same rule -- without that, an unconditional rate clamp there would have quietly rewritten a carried-over value back down on the very next undo step. Live preview needed no changes at all: a machine switch already only pushes new params to the running `RealtimeStretchPlayer`, which (correctly) restarts the sample from position 0 on the next commit rather than tearing down the engine -- exactly "preview keeps running, sample restarts at the top," which the user explicitly said was fine.
2. **New "Defaults" button**, next to Revert, since a machine switch no longer resets anything on its own. Knobs-only: resets every parameter to the current machine's defaults but keeps the processed render (`_resetToMachineDefaults`, `ContentView.swift`) -- unlike Revert, which does the same reset but also discards the render. Revert is unchanged.
3. **The MACHINES sidebar filter field is gone.** With a hand-groupable 10-machine roster it wasn't earning its keep; `_groupedMachines` now just groups `StretchProcessor.allMachines` by manufacturer with no text-filtering step.

**Known accepted regression:** `_renderIsStale` compares whole snapshots, so a carried-but-parked value can now make it report "stale" on a re-render that would actually be byte-identical (e.g. a parked stretch value that a detour through a stricter machine happened to clamp along the way). Documented, not fixed -- the real fix is a `effective(for:)` projection that zeroes params a machine ignores before comparing, which is real work deferred past this release.

### Why not AVAudioFile

Tried first, dropped deliberately. On this machine's SDK (macOS 26.5 SDK / Xcode 26.6), `AVAudioFile` has two reproducible bugs that break the bit-exactness this app depends on: reading 16-bit PCM via `commonFormat: .pcmFormatInt16` silently truncates the frame count (a 44100-frame file came back as 42969 frames — confirmed via both `AVAudioFile` and raw `ExtAudioFile`), and a WAV file `AVAudioFile` itself writes (with its automatic JUNK/FLLR alignment padding) comes back with `length == 0` when reopened. Full repro notes are in `WavCodec.swift`'s header comment. `WavCodec.swift`/`AiffCodec.swift` read and write raw PCM bytes directly instead — no framework in between, nothing to silently mis-round.

## Design notes worth knowing before touching StretchEngine.cpp / RealtimeStretchPlayer.cpp

- **Two engines, two threading models, on purpose.** `AkzStretchEngine`/`StretchProcessor` is synchronous and allocates on whatever thread calls `process()` — correct for offline rendering (Process/Save), unsafe on a CoreAudio render thread. `AkzRealtimePlayer`/`RealtimePlayer` wraps a background thread that does the same recompute and publishes via `std::atomic_load`/`store` on a `shared_ptr` so `pull()` never allocates or blocks — used only for live audition. Don't try to make one serve both jobs.
- **`pull()`'s shared_ptr publish is not strict wait-free lock-free audio programming** (libc++'s shared_ptr atomics use an internal spinlock) — a deliberate, documented tradeoff for a personal-use app. ThreadSanitizer-clean and stress-tested (`RealtimeStretchPlayerTests.cpp`), but don't build a shipped plugin's real-time path on this unmodified.
- **CLASSIC quantises output length to whole cycle-length blocks and does not correct the resulting timing error.** That imprecision is the documented, authentic behaviour ("perfect pitch, imprecise timing") — see `AkzEngine_Classic` in `AkaizerCore.h`. Don't "fix" it.
- **REVISED synthesises the same block-quantised audio, then linearly resamples to the exact requested length.** That resample is what introduces REVISED's documented slight pitch drift — it falls out of the implementation rather than being a bolted-on effect.
- **INTELLIGENT mode currently falls back to the CYCLIC synthesis path.** Splice-point analysis (autocorrelation/AMDF-driven boundaries, plus the `quality`/`width` parameters that only apply in this mode) is not yet implemented.
- **Every `AkzMachineProfile` field is cited** in `MachineProfile.cpp` as `[M]` (manual-confirmed), `[F]` (forum/secondary source), or `[I]` (this project's inference). Check the citation before changing a value.
